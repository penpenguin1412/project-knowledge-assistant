# 五分钟演示

全部使用 examples 中的自编虚构资料。先启动服务，保持终端运行。

1. **0:00–0:40 场景与范围**：打开页面，点击「载入示例项目」，查看两份项目资料。说明当前是本机应用、非线上企业部署。
2. **0:40–1:40 可追溯证据**：问“项目交付物有哪些？”，使用原文检索模式；展开出处，核对文件、行号和逐字文本。准确说明这是检索结果。已配置真实模型时可切换调用，展示每条事实的引用。
3. **1:40–2:20 不确定性**：问“座椅采购预算具体是多少元？”。原文检索可能返回“尚未确定”，它不能代替模型作答；真实模式应依据资料拒答或说明未确定，实际输出写进评测，不预先声称成功。
4. **2:20–3:30 行动确认**：进入会议转待办，填入示例，规则提取产生三条草稿。展示未知负责人/截止日期仍为空，以及清单中没有新增待办。修改一项、取消勾选一项，再勾选人工核对确认并入库。
5. **3:30–4:10 持久化**：更新一项状态为“进行中”，保存；刷新页面后再打开清单，核对修改仍存在。
6. **4:10–5:00 验证与局限**：打开运行记录展示输入、耗时和引用；展示 reports/baseline.md。报告 18/18 原文命中，不称为模型回答正确率；指出 7 个不可回答问题仍有相关片段这一真实局限。

已接入本机 Codex 时，用 `start-codex.ps1` 启动；可展示真实问答和 `reports/live-20260911T164510Z.md`。30 题中实际调用模型 25 次，5 题在检索阶段拦截；12 道不可回答题均拒答。这不是经过人工评分的 100% 准确率。

可展示的异常：重复上传同一内容；上传空文本；未配置模型时切换真实模式；空项目提问。不要在现场临时发送私人合同给云端，不展示密钥或私人运行记录。

讲解重点：为什么待办要人工确认，为什么出处存在不等于回答正确，为什么选择单人本机版本，如何从失败样本决定下一步改进。不要把 AI 生成的全部代码表述为独立手写，也不将 Dify 的平台能力写成自己的实现。
